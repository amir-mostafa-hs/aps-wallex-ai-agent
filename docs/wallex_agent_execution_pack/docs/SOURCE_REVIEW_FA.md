# بازبینی دوباره منابع اصلی هکاتون — منبع‌محور

نسخه: 1.2 · تاریخ بازبینی: 2026-10-22

این سند خلاصه‌ای منبع‌محور از چهار فایل اصلی است. در صورت نیاز به نقل دقیق، خود فایل حفظ‌شده در `source_materials/originals/` مرجع است. موارد استنباطی از متن منبع جدا شده‌اند.

## 1. `intro-text.md` — معرفی چالش

- هدف: ساخت Agent که داده بازار را بگیرد، تحلیل کند، پیشنهاد خرید/فروش بسازد و معامله را به‌صورت خودکار مطابق الگوریتم انجام دهد.
- داوری بر موتور معاملاتی، منطق و الگوریتم متمرکز است؛ UI اولویت اصلی نیست.
- ابزارهای قابل استفاده شامل AI، تحلیل داده، Coding Agent، Agentic AI، Wallex API و Wallex MCP هستند.
- Backtest روی داده تاریخی و Shadow Test روی بازار جاری بدون ارسال سفارش واقعی پیشنهاد شده‌اند.
- ویدیوی دموی اجباری باید ارسال شود؛ متن می‌گوید بدون ارسال آن پروژه وارد داوری نمی‌شود.
- قوانین مورد تأکید: بازارهای مجاز، ممنوعیت معامله دستی، معامله درون‌تیمی و Wash Trading.
- تکرارپذیری و قابلیت بررسی فنی در کنار سود خالص اهمیت دارند.

## 2. `task.md` — صورت مسئله و داوری

- توسعه و اجرا در سه روز انجام می‌شود؛ سرمایه مبنای ذکرشده ۵,۰۰۰,۰۰۰ تومان است و یک حساب اختصاصی برای تیم در نظر گرفته شده.
- سیستم باید داده بازار را دریافت/تحلیل کند، فرصت‌ها را بشناسد، خرید و فروش را الگوریتمی انجام دهد، مدیریت سرمایه/ریسک داشته باشد و اجرای مجددپذیر باشد.
- برداشت/واریز حساب چالش غیرفعال است؛ معاملات دستی، Self-Trading، معاملات هماهنگ درون‌تیمی و Wash Trading ممنوع‌اند.
- فرمول بازدهی در متن آمده است: `((ارزش نهایی حساب − سرمایه اولیه) / سرمایه اولیه) × 100`؛ هزینه معاملات هم باید منظور شود.
- متن هم می‌گوید ارزش نهایی دارایی‌ها و حتی unrealized P&L در صورت وجود در ارزش حساب لحاظ می‌شود و هم بلافاصله تأکید می‌کند سود یا زیان باید در تومان محقق شود و پایان نباید کوین باقی مانده باشد. برای اجرای پروژه، این دو عبارت را پنهانی یکی فرض نمی‌کنیم: معیار داخلی realized net P&L و equity نهایی جدا گزارش می‌شوند؛ موعد رسمی پایان و نحوه ارزش‌گذاری با برگزارکننده تأیید می‌شود و برنامه عملیاتی برای خروج/تبدیل دارایی قبل از پایان در نظر گرفته می‌شود.
- سورس تحویلی باید با نسخه‌ای که معامله کرده دقیقاً مطابقت کند. GitHub، مستند Markdown، توضیح معماری/منطق/AI/API/ریسک، لاگ علت هر معامله و ویدیوی حدود ۵ دقیقه از موارد تحویلی‌اند.
- جدول امتیازدهی در متن به‌صورت «پیشنهاد امتیازدهی» معرفی شده؛ کاربر آن را به‌عنوان جدول کاری مسابقه در اختیار گذاشته است. برای برنامه‌ریزی همین جدول ۳۰۰ امتیازی استفاده می‌شود، ولی در بسته به‌عنوان متن نقل‌شده/ارائه‌شده معرفی می‌شود، نه ادعای تأیید مستقل برگزارکننده.

## 3. `assets.md` — حساب Spot اعتباری و نمادهای غیرفعال

- کاربر صریحاً افزوده که ترید فقط Spot و بدون لوریج است.
- متن می‌گوید تمام بازارهای والکس به‌استثنای بازارهای فهرست‌شده در حساب اعتباری قابل معامله‌اند. فایل ۳۴۵ سطر جفت‌ارز مطابق الگوی `BASE/TMN` یا `BASE/USDT` دارد؛ تعداد جفت‌های یکتا ۳۴۵ و تکراری‌ها صفر است.
- جفت‌ها در `source_materials/derived/inactive_markets.json` فقط به‌عنوان denylist استخراج شده‌اند.
- این denylist ثابت جایگزین بررسی بازار فعال فعلی API نیست؛ ابتدا market metadata را دریافت کنید، موارد فعال/Spot را نگه دارید، denylist را حذف کنید و سپس capability و حداقل‌های سفارش در حساب واقعی را بررسی کنید.

## 4. `هکاتون استارکوچ _ والکس.pdf` — جزئیات حساب اعتباری

### صفحه ۱

- تیتر طرح می‌گوید «۰ تومان دارایی ورودی + ۵,۰۰۰,۰۰۰ تومان اعتبار دریافتی برای ۳ روز».
- شرایط دریافت طرح شامل احراز هویت پایه و کافی بودن موجودی حساب برای ثبت‌نام است؛ در کنار تیتر صفر دارایی ورودی، این شرط ممکن است به احراز صلاحیت/وضعیت حساب مربوط باشد. حد دقیق را باید از حساب/برگزارکننده تأیید کرد.
- با فعال‌سازی، حساب جانبی «حساب اعتباری» ساخته می‌شود؛ پس از پایان یا توقف طرح، PDF می‌گوید دارایی‌های آن در بخش فروش آنی فروخته شده و طبق قواعد طرح به حساب اصلی منتقل می‌شوند.
- جدول امکانات، معامله پیشرفته، خرید/فروش آنی و ساخت/مدیریت API را برای حساب اعتباری نیز نشان می‌دهد؛ معامله تعهدی و قابلیت بومی «بات معامله‌گر» برای حساب اعتباری علامت فعال ندارند. این مانع ساخت ربات سفارشی از طریق API نیست، ولی باید اتصال خصوصی با read-only preflight اثبات شود.

### صفحه ۲

- بازپرداخت اعتبار شامل اصل اعتبار و کارمزد طرح است؛ مثال عمومی یک طرح ۳۰روزه را با کارمزد ۶۰۰,۰۰۰ تومان، یعنی ۲۰,۰۰۰ تومان در روز، توضیح می‌دهد.
- بنر PDF صریحاً «بازپرداخت اعتبار ۳ روزه رایگان» می‌گوید. چون این بنر و توضیح عمومی کارمزد در کنار هم آمده‌اند، قبل از معامله باید شرایط دقیق همین طرح سه‌روزه از صفحه واقعی حساب یا برگزارکننده تأیید شود؛ از مثال ۳۰روزه، کارمزد طرح هکاتون را محاسبه یا فرض نکنید.
- با کاهش ارزش دارایی‌های حساب اعتباری و رسیدن به حد هشدار، پیامک/نوتیفیکیشن اعلام می‌شود. اگر افت ادامه یابد، متن می‌گوید دارایی‌های اعتباری به‌صورت آنی فروخته و حساب لیکویید می‌شود؛ در صورت لیکوییدشدن هیچ دارایی یا مبلغی به کاربر بازنمی‌گردد.
- متن صریحاً انتقال از حساب اصلی به حساب اعتباری را یکی از راه‌های پیشگیری از لیکوییدشدن ذکر می‌کند. جدول صفحه اول قابلیت انتقال بین حساب‌ها را زیر حساب اصلی فعال و زیر حساب اعتباری غیرفعال نشان می‌دهد؛ این با امکان انتقال یک‌طرفه از اصلی به اعتباری سازگار است. پیش از اتکا در عملیات خودکار، روش واقعی این انتقال و دسترسی حساب را در UI/API تأیید کنید؛ انتقال از credit به main را فرض نکنید.
- کارمزد معاملات حساب اعتباری از سطح ۱ شروع می‌شود؛ هزینه واقعی سفارش باید در expected edge و P&L منظور شود.

## 5. پیامدهای مستقیم برای محصول

1. Live default-off و fail-closed باقی می‌ماند تا دسترسی API، موجودی، نمادها، حداقل سفارش، tick/step size، نرخ درخواست و fee تأیید شده باشند.
2. پیش از اولین معامله، سناریوی liquidation، thresholdهای هشدار حساب و مسیر stop/exit باید فهمیده و آزموده شوند. stop distance در JSON مدل، به‌تنهایی اجرای stop واقعی نیست.
3. چون پایان طرح ممکن است دارایی را با Instant Sell ببندد و لیکوییدشدن خطر جدی دارد، ربات باید پوزیشن‌ها، زمان مانده تا پایان طرح و شرایط خروج را مانیتور کند. ساعت دقیق پایان هکاتون/اعتبار هنوز باید از برگزارکننده گرفته شود.
4. برای گزارش، realized net P&L به تومان، equity/value نهایی حساب، دارایی باقی‌مانده، unrealized P&L، fee و drawdown جدا ثبت شوند؛ مبنای رسمی را با برگزارکننده تطبیق دهید.
5. حجم معامله و turnover ثبت می‌شود، اما نباید به شکل مصنوعی ایجاد شود؛ Wash/Self Trading تخلف است.

## 6. مواردی که همچنان تأیید زنده می‌خواهند

- دسترسی همین API key به **همان حساب اعتباری** و permissionهای واقعی.
- بازارهای فعلی API و active Spot بودن هر نماد باقی‌مانده از denylist.
- fee واقعی حساب اعتباری و آیا کارمزد اعتبار ۳روزه برای همین طرح صفر است.
- حد هشدار و liquidation دقیق و امکان/محدودیت سفارش Stop در والکس.
- ساعت دقیق پایان اعتبار و رقابت، الزام قطعی به بستن موقعیت‌ها و روش official scoring در پایان.
- endpointهای فعلی، schema، authentication، rate limit و رفتار سفارش timeout/partial fill.
