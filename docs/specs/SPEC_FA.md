# مشخصات محصول — Wallex Opportunity Agent

نسخه: 0.1 · وضعیت: قابل‌پیاده‌سازی با چند مورد نیازمند تأیید فنی

## 1. هدف محصول

ساخت Agent خودکار معاملات Spot در حساب اعتباری اختصاصی هکاتون والکس که در طول مسابقه بازارهای مجاز را اسکن کند، برای هر بازار فرصت و افق زمانی مناسب را ارزیابی کند، سرمایه را بر اساس کیفیت فرصت و وضعیت کل حساب تخصیص دهد، ورود/خروج را مدیریت کند و شواهد کامل برای ارزیابی فنی و گزارش معاملات تولید کند.

موفقیت فقط سود نیست. طبق جدول امتیازدهی ارائه‌شده، سیستم باید به سود نهایی، کنترل افت سرمایه، فعال‌بودن الگوریتم، پایداری اجرا، منطق استراتژی، استفاده واقعی از AI، مدیریت سرمایه، تکرارپذیری و Backtest/Shadow Test پاسخ بدهد.

## 3. اصول دامنه

- حساب معاملاتی: حساب اعتباری اختصاصی هکاتون.
- نوع معامله: Spot؛ هیچ معامله تعهدی/لوریج‌دار در نسخه اول.
- سرمایه مبنای مسابقه در `task.md`: ۵,۰۰۰,۰۰۰ تومان؛ PDF حساب اعتباری را «۰ تومان دارایی ورودی + ۵,۰۰۰,۰۰۰ تومان اعتبار برای ۳ روز» معرفی می‌کند. مبلغ ۵ میلیون را دوبار نشمارید. پیش از Live موجودی/available balance واقعی و نحوه اعمال اعتبار را از API و صفحه حساب تطبیق دهید. در PDF ریسک liquidation جدی است و گفته شده پس از liquidation دارایی/مبلغی بازنمی‌گردد.
- ورود: خرید دارایی با سرمایه آزاد؛ خروج: فروش موجودی همان پوزیشن. Short-selling در دامنه نیست.
- بازارها: اصل `source_materials/originals/assets.md` منبع denylist حساب اعتباری است؛ نسخه مشتق‌شده دارای ۳۴۵ جفت‌ارز در `source_materials/derived/inactive_markets.json` است. نماد فقط وقتی مجاز است که در denylist نباشد، API آن را فعال Spot نشان دهد و حساب امکان معامله آن را داشته باشد. فایل مشتق‌شده جای اصل را نمی‌گیرد.
- افق زمانی: تطبیقی؛ سیستم می‌تواند از میان افق‌های مجاز ازقبل‌تعریف‌شده انتخاب کند، اما در نسخه اول بازه‌ها و قواعد باید ثابت و قابل‌آزمایش باشند.
- داده ورودی نسخه اول: قیمت، کندل/بازده، حجم، اسپرد، عمق بازار/imbalance و نوسان. خبر و تحلیل فاندامنتال برای نسخه بعدی است.
- امکان چند پوزیشن هم‌زمان با محدودیت ریسک پرتفوی وجود دارد.
- Backtest، Shadow Test و Live باید از یک قرارداد سیگنال/استراتژی استفاده کنند تا اختلاف نتایج کاهش یابد.
- چارچوب Agent: LangChain برای orchestrating تصمیم AI و تولید TradeIntent ساختاریافته؛ داده/زمان‌بندی/ریسک/اجرا در لایه‌های قطعی و مستقل باقی می‌مانند.
- زمان‌بندی پایه قابل‌تنظیم است: اسکن feature هر ۱۵ ثانیه؛ refresh خلاصه بازار حدود ۳۰ ثانیه؛ بازبینی عمیق AI حداکثر هر ۳۰ ثانیه و حداکثر ۳ بار در دقیقه. این تنظیمات بعد از بررسی محدودیت API و سرعت provider تأیید یا تغییر داده می‌شوند.

## 4. رفتار مورد انتظار

### 4.1 اسکنر بازار

1. فهرست نمادها را از API رسمی دریافت کند.
2. denylist محلی از `assets.md` را اعمال کند.
3. بازارهای غیرفعال، با حداقل مقدار/ارزش غیرقابل‌اجرا یا نقدشوندگی نامناسب را کنار بگذارد.
4. ویژگی‌های بازار را برای چند افق مشخص محاسبه کند.
5. همه بازارهای معتبر را بر مبنای market summary و داده cacheشده سبک اسکن کند و فقط Candidateهای برتر را برای ارزیابی AI انتخاب کند.
6. stream عمومی قیمت/معاملات/عمق را در صورت پشتیبانی و تأیید مستندات مصرف کند؛ برای همه بازارها اتصال WebSocket نامحدود فرض نشود.
7. کندل‌ها OHLCV هستند، نه تصویر چارت: تاریخچه از endpoint کندل تأییدشده گرم‌سازی می‌شود و در صورت نیاز، کندل‌های ۵ و ۱۵ دقیقه‌ای به‌صورت محلی از کندل ۱ دقیقه‌ای ساخته می‌شوند.
8. در نبود تاریخچه کافی یا داده تازه، نماد به AI/اجرای معامله راه پیدا نکند؛ داده ساختگی نباید به‌عنوان بازار واقعی استفاده شود.

### 4.2 AI Decision Agent

برای Candidateهای منتخب، AI باید واقعاً یک تصمیم بگیرد، نه اینکه صرفاً سیگنال ثابت را توضیح دهد. خروجی باید JSON معتبر و محدود به schema باشد و حداقل شامل این فیلدها شود:

```json
{
  "symbol": "<approved-symbol>",
  "action": "BUY | HOLD | EXIT",
  "strategy_id": "momentum | trend_following | mean_reversion",
  "horizon": "1m | 5m | 15m | 1h",
  "confidence": 0.0,
  "entry_reason": "string",
  "invalidation_condition": "string",
  "stop_distance_pct": 0.0,
  "take_profit_distance_pct": 0.0,
  "max_holding_minutes": 0,
  "parameter_overrides": {},
  "evidence_ids": []
}
```

Schema نمونه اولیه است و باید با قرارداد واقعی پیاده‌سازی شود. Action و strategy فقط از enumهای مجاز انتخاب می‌شوند. پارامترهای بیرون از محدوده رد می‌شوند. هیچ توضیح متنی آزاد به‌تنهایی سفارش را فعال نمی‌کند.

نکته پیاده‌سازی: `TypedDict` فقط قرارداد نوع‌دهی/ساختار را بیان می‌کند و به‌تنهایی داده زمان اجرا را validate نمی‌کند. پس خروجی مدل باید قبل از تصمیم Risk Engine با validator صریح Python کنترل شود؛ خروجی نامعتبر به `NO_TRADE` تبدیل می‌شود.

LangChain باید با خروجی ساختاریافته مبتنی بر `TypedDict` یا JSON Schema استفاده شود؛ تعریف مدل Pydantic در کد پروژه الزامی نیست. پس از دریافت خروجی، validator قطعی باید enumها، دامنه اعداد، symbol مجاز و سازگاری فیلدها را بررسی کند. context مدل باید شامل featureهای مشتق‌شده از کندل‌های ۱m/۵m/۱۵m/۱h، spread/cost، freshness و وضعیت پرتفوی باشد؛ نه تصویر چارت و نه تمام tickها. در Spot، `BUY` ورود/افزایش مجاز پوزیشن و `EXIT` فروش موجودی همان پوزیشن است؛ short مجاز نیست.

اگر مدل timeout داد، خروجی نامعتبر بود، داده قدیمی بود یا Candidate دیگر معتبر نبود، تصمیم پیش‌فرض `NO_TRADE/HOLD` است؛ نه ثبت سفارش حدسی.

### 4.3 تخصیص پرتفوی

- Candidateها به‌صورت مستقل تحلیل و سپس در سطح پرتفوی رتبه‌بندی می‌شوند.
- مبلغ معامله بر اساس کیفیت سیگنال، نوسان، نقدشوندگی، فاصله حد ضرر، سرمایه آزاد، ریسک پوزیشن‌های باز و مواجهه تجمعی تعیین می‌شود.
- سرمایه آزادشده از معامله قبلی تنها منبع مجاز تخصیص نیست؛ تصمیم از کل موجودی آزاد قابل‌استفاده گرفته می‌شود.
- استفاده از ۱۰۰٪ سرمایه مجاز نیست؛ ذخیره نقدی باید باقی بماند.
- سرمایه تخصیص‌یافته با ریسک تا Stop و حد notional هم‌زمان محدود می‌شود؛ این دو مفهوم یکی نیستند.

### 4.4 خروج و یادگیری

- خروج تطبیقی با توجه به قیمت/حجم، افق زمانی، تغییر سیگنال و شرایط بازار مدیریت می‌شود.
- Risk Engine حد ضرر، maximum holding time، drawdown و توقف اضطراری را enforce می‌کند.
- استراتژی‌های تأییدشده و پارامترهای مجاز می‌توانند در اجرای زنده انتخاب/تنظیم شوند.
- استراتژی جدید یا تغییر اساسی ابتدا در Backtest/Shadow آزموده می‌شود و خودکار به Live promotion نمی‌شود.
- زیان معامله به‌خودی‌خود اثبات نمی‌کند استراتژی بد است؛ یادگیری باید با شواهد و حداقل نمونه معقول انجام شود.

### 4.5 لاگ معامله و تحلیل زیان

برای هر چرخه و سفارش/معامله ذخیره شود:

- timestamp UTC و شناسه cycle، symbol، mode، strategy ID، horizon و شناسه prompt/model؛
- snapshotهای مورد استفاده یا شناسه/هش داده، ویژگی‌ها و امتیاز Candidate؛
- تصمیم ساختاریافته AI، confidence، thesis، invalidation و دلیل رد/قبول توسط Risk Engine؛
- قیمت درخواست‌شده، مقدار، client order ID، وضعیت‌های سفارش، fills، میانگین قیمت، fee و زمان‌بندی؛
- P&L ناخالص/خالص تحقق‌یافته، هزینه و currency کارمزد، مدت نگهداری، MFE/MAE در صورت امکان؛
- برای زیان: دلیل تأییدشده / محتمل / نامشخص، شواهد، فرضیه علت و اقدام بعدی.

مدل نباید برای زیان، علت قطعی جعل کند. رخداد فاندامنتال تنها در صورتی ثبت می‌شود که منبع یا داده قابل‌تأیید در دسترس باشد؛ در نسخه اول خبرخوان فعال در دامنه نیست.

### 4.6 اجرای سفارش

- state machine صریح سفارش: `CREATED → SUBMITTED → PARTIALLY_FILLED → FILLED/CANCELLED/REJECTED/UNKNOWN`.
- هر سفارش `client_id` یکتا داشته باشد، مشروط به تأیید معنا/رفتار این فیلد در API فعلی.
- اگر POST timeout شد، قبل از هر retry وضعیت سفارش با `client_id` یا endpoint رسمی query شود؛ بدون reconciliation سفارش جدید ثبت نشود.
- پس از restart، موجودی، سفارش‌های باز و معاملات اخیر از API reconcile شوند.
- حداکثر یک writer فعال برای اجرای سفارش؛ lock بین processها.
- در یک symbol نباید سفارش‌های باز متقابل از طرف همین استراتژی وجود داشته باشد که امکان self-trade ایجاد کنند. پیش از reversal، سفارش متضاد cancel و وضعیت cancel تأیید شود.
- حجم معامله برای امتیازگیری به‌صورت مصنوعی تولید نشود؛ Wash/Self Trading ممنوع است.

## 6. خارج از دامنه نسخه اول

## 7. مواردی که در Spike فنی باید قطعیت پیدا کنند

1. endpoint دقیق و schema فعلی برای فهرست Spot markets، candles/history، ticker، order book، balance/account، open orders، cancel، trades و order details.
2. دسترسی همین API Key به حساب اعتباری و معنای موجودی/سرمایه قابل‌استفاده.
3. رفتار `client_id`، نرخ محدودیت endpointها، precision / tick size / step size / min-notional.
4. امکان تبدیل P&L و fee به تومان برای هر بازار منتخب.
5. دسترسی واقعی به داده تاریخی کافی برای Backtest و محدودیت نرخ API.

تمام موارد بالا باید با مستندات فعلی `developers.wallex.ir/docs` و تست read-only تأیید شوند؛ نمونه‌های قدیمی یا برداشت از نام endpoint جایگزین تأیید نیستند.

### سیاست‌های اجرایی پیرامون موارد نامشخص (Open Questions Directives):
- **Stop Loss و خروج اضطراری:** عدم اتکا به شرطی‌های صرافی تا زمان اثبات؛ پیاده‌سازی دیده‌بان محلی (Local Watchdog) مستقل از LLM برای پایش قیمت و خروج اضطراری؛ ثبت ریسک‌های قطعی شبکه/توقف پروسس و الزام تست آن پیش از Live.
- **حداقل ارزش اسمی سفارش (Min Notional):** مقادیر ۱۰۰ هزار تومان و ۱۰ تتر صرفاً پیش‌فرض‌های اولیه و قابل‌تنظیم در کانفیگ هستند و حداقل رسمی والکس تلقی نمی‌شوند؛ معامله هر بازار منوط به استعلام مستندات/پاسخ واقعی API است و در صورت عدم تأیید، بازار مسدود (Fail-Closed) می‌ماند.
- **زمان انقضای اعتبار:** استعلام زمان دقیق و منطقه زمانی از `expireAt`؛ عدم اتکای کور به فرض ۷۲ ساعت؛ توقف ورود جدید با نزدیک‌شدن به انقضا؛ پیشنهاد محافظه‌کارانه خروج کامل ۲ ساعت پیش از انقضا مشروط به تایید کاربر؛ در صورت عدم قطعیت انقضا، Live مسدود می‌ماند.
- **سند عملیاتی ردیاب محلی:** جزئیات User Storyها، درزهای آزمون و Preflight Checklist در [.scratch/wallex-opportunity-agent/spec.md](file:///.scratch/wallex-opportunity-agent/spec.md) تثبیت شده‌اند.


## پیوست منبعی مهم: حساب اعتباری

- طبق PDF، ساخت و مدیریت API برای حساب اعتباری فعال است، در حالی که قابلیت بومی بات معامله‌گر و معامله تعهدی برای اعتبار فعال نشان داده نشده است؛ اتصال ربات سفارشی از API باید read-only preflight شود.
- PDF کارمزد معامله حساب اعتباری را از سطح ۱ می‌داند و برای طرح اعتبار، هشدار liquidation می‌دهد. بنر «بازپرداخت اعتبار ۳ روزه رایگان» با مثال عمومی fee طرح ۳۰روزه کنار هم است؛ هزینه واقعی این طرح را تأیید کنید.
- متن PDF انتقال از حساب اصلی به اعتباری را راه پیشگیری از liquidation ذکر می‌کند و جدول آن را در ستون حساب اصلی فعال نشان می‌دهد؛ قابلیت واقعی انتقال main→credit را پیش از اتکا تأیید کنید و انتقال credit→main را فرض نکنید.
- `task.md` می‌گوید در پایان نباید دارایی کوینی باقی بماند و سود/ضرر به تومان تحقق یابد؛ هم‌زمان فرمول بازدهی از ارزش نهایی دارایی‌ها و unrealized P&L نیز نام می‌برد. گزارش سیستم باید realized net P&L و equity نهایی را جدا ارائه کند، و خروج نهایی با زمان رسمی مسابقه هماهنگ شود.
