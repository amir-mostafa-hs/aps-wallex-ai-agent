# تاریخچه Grill-me و ردیابی تصمیم‌های محصول

نسخه: 1.0 · تاریخ تجمیع: 2026-10-22

این سند تصمیم‌های گفت‌وگوی محصول را به ترتیب تقریبی مصاحبه ثبت می‌کند تا دلیل تصمیم‌ها در کنار Spec بماند. برای مقادیر و قرارداد نهایی، به `DECISION_REGISTER_FA.md` و `AGENT_CONTRACT_FA.md` رجوع کنید؛ این تاریخچه جایگزین آن دو نیست.

## 1. هدف و محدودیت زمانی

- محصول، AI Trading Agent برای هکاتون AI Agent استار کوچ/والکس است.
- زمان توسعه کمتر از سه روز و هدف برنامه‌ریزی، تکمیل نسخه اجرایی طی 48 ساعت و سپس ادامه اجرای ربات برای جمع‌آوری گزارش معاملات است.
- هدف صرفاً سود کوتاه‌مدت نیست؛ امتیاز فنی، کنترل ضرر، فعالیت معقول، پایداری اجرا، منطق استراتژی، نقش واقعی AI، قابلیت اجرای مجدد و شواهد Backtest/Shadow نیز اهمیت دارند.
- نیاز مشاهده‌پذیری و مدیریت عملیاتی مطرح شد؛ UI تزئینی از موتور معاملاتی کم‌اهمیت‌تر است.

## 2. روش کشف نیاز و تصمیم‌ها به ترتیب

### 2.1 اسکن فرصت‌ها به‌جای تمرکز بر یک نماد

**پرسش:** آیا ایده استراتژی از قبل مشخص است؟

**تصمیم کاربر:** همه بازارهای مجاز اسکن شوند؛ هر جا فرصت کوتاه‌مدت مناسب پیدا شد، سیستم بتواند وارد معامله شود. استراتژی از پیش ثابت نیست و دست تیم برای انتخاب باز است.

**نتیجه طراحی:** scanner همه بازارها را مستقل ارزیابی می‌کند؛ سپس فرصت‌ها در سطح پرتفوی رتبه‌بندی می‌شوند. ممکن است یک بازار سیگنال داشته باشد و بازار دیگری نداشته باشد.

### 2.2 هدف تطبیقی، نه انتظار برای فرصت ایده‌آل

**پرسش:** فعالیت زیادتر یا معامله کمتر اما بسیار گزینشی؟

**تصمیم کاربر:** رویکرد تطبیقی؛ در زمان محدود، سیستم نباید بیش از حد منتظر فرصت کاملاً استثنایی بماند. فرصت عادی اما قابل‌قبول را بگیرد، بدون تضعیف Risk Management.

**نتیجه طراحی:** threshold ورود تطبیقی است، اما هر ورود باید هزینه‌های fee/spread/slippage را پوشش دهد و مزیت خالص مثبت و قابل‌دفاع داشته باشد. تعداد معامله به هر قیمت هدف نیست.

### 2.3 تخصیص سرمایه و پوزیشن‌های هم‌زمان

**پرسش:** سرمایه چگونه بین چند Candidate تقسیم شود؟

**تصمیم کاربر:** تخصیص تطبیقی با توجه به کیفیت سیگنال، نوسان، نقدشوندگی، ریسک و سرمایه آزاد؛ چند پوزیشن باز می‌تواند هم‌زمان وجود داشته باشد، با سقف ریسک و سرمایه درگیر.

**توضیح کاربر:** سرمایه معامله فقط از درآمد آزادشده معامله قبلی تأمین نشود؛ سیستم می‌تواند از کل سرمایه آزاد و قابل‌استفاده حساب استفاده کند، اما نباید کل موجودی را وارد بازار کند.

**نتیجه طراحی:** Portfolio Allocator، cash reserve، max position notional، max aggregate exposure، max positions و risk-to-stop مستقل محاسبه می‌شوند. ریسک پولی با notional یکسان فرض نمی‌شود.

### 2.4 افق زمانی و نقش واقعی ایجنت

**پرسش:** افق ثابت باشد یا سیستم انتخاب کند؟

**تصمیم کاربر:** افق زمانی و نوع رفتار معامله با توجه به شرایط هر بازار و مدیریت ریسک تطبیقی باشد؛ این‌که Agent بتواند خودش انتخاب کند مزیت مهم آن است.

**پرسش:** سطح آزادی استراتژی؟

**تصمیم کاربر:** شروع از Option B: انتخاب استراتژی‌های مشخص و تغییر پارامترهای مجاز؛ حرکت تدریجی به سمت Option C، یعنی تولید و آزمایش فرضیه‌های جدید.

**پرسش:** آیا Agent در اجرای زنده هر تغییری را فوری اعمال کند؟

**تصمیم کاربر:** گزینه C ترکیبی انتخاب شد: جابه‌جایی بین استراتژی‌های ازقبل‌تأییدشده و تنظیمات مجاز می‌تواند در اجرا انجام شود؛ استراتژی جدید یا تغییر اساسی ابتدا باید Backtest/Shadow شود.

**نتیجه طراحی:** یک LangChain Decision Agent؛ نه swarm سنگین. Agent نقش واقعی در انتخاب Candidate/strategy/horizon/parameters دارد، اما مستقیماً ابزار نوشتنی ارسال/لغو سفارش نمی‌گیرد.

### 2.5 فعال‌بودن الگوریتم در نبود فرصت

**تصمیم کاربر:** threshold تطبیقی باشد؛ فرصت عادی و قابل‌قبول نیز گرفته شود، اما کنترل ریسک ضعیف نشود.

**نتیجه طراحی:** `NO_TRADE` همچنان action معتبر است. اگر مزیت خالص قابل‌قبول نیست، معامله انجام نمی‌شود؛ این شرط نباید صرفاً برای افزایش turnover حذف شود.

### 2.6 نوع معاملات و کاربرد سرمایه آزاد

**پرسش:** مدیریت موجودی چند دارایی یا خرید و فروش ساده؟

**تصمیم کاربر:** با محدودیت زمانی، روش الف مناسب‌تر است: خرید Spot با موجودی آزاد و فروش بعدی دارایی متعلق به همان پوزیشن؛ سپس فرصت‌های جدید بررسی شوند. سیستم مجبور نیست فقط از سرمایه آزادشده همان معامله استفاده کند.

**نتیجه طراحی:** Spot long-only؛ بدون short، leverage یا derivatives. در MVP هر نماد حداکثر یک پوزیشن Agent-owned دارد و ورود جدید روی پوزیشن/سفارش نامشخص همان نماد رد می‌شود.

### 2.7 مدیریت خروج

**پرسش:** حد سود/ضرر ثابت، خروج تماماً AI یا ترکیبی؟

**تصمیم کاربر:** گزینه ترکیبی؛ Agent خروج تطبیقی پیشنهاد دهد اما سقف‌های قطعی ریسک مستقل باشند.

**نتیجه طراحی:** hard stop، max holding time، drawdown gate و kill switch نباید منتظر مدل باشند. سازوکار عملی stop (exchange conditional order یا local watchdog) باید با API جاری اثبات و تست شود؛ تنها ثبت یک درصد در TradeIntent به معنی اجرای stop واقعی نیست.

### 2.8 یادگیری و تحلیل زیان

**پرسش:** Agent چگونه از معاملات قبلی نتیجه بگیرد؟

**تصمیم کاربر:** گزینه ترکیبی؛ عملکرد هر بازار/استراتژی مستقل ارزیابی شود و وضعیت کلی بازار و پرتفوی هم لحاظ شود. در صورت زیان، لاگ و دلیل آن (اگر شواهدی وجود دارد) ثبت شود؛ گاهی ممکن است علت نامشخص باشد یا یک رخداد بیرونی ناگهانی رخ دهد.

**نتیجه طراحی:** لاگ thesis، evidence، entry/exit, fill/fee, realized net P&L و classification علت `confirmed / likely / unknown`. مدل اجازه ندارد علت خبر یا اتفاقی را بدون شاهد واقعی جعل کند. یک معامله زیان‌ده به‌تنهایی باعث تغییر استراتژی زنده نمی‌شود.

### 2.9 خبر و فاندامنتال

**تصمیم کاربر:** نسخه اول گزینه A — تمرکز بر رفتار قیمت و بازار، نه سامانه فعال خبرخوان. معاملات کوتاه‌مدت‌اند و خبر ممکن است تا رسیدن به سیستم اثرش را گذاشته باشد. گزینه C (افزودن اخبار قابل‌اتکا کنار قیمت/حجم) برای فاز آینده باقی می‌ماند.

### 2.10 Backtest، Shadow و Live

**پرسش:** ابتدا تمام تست‌ها تمام شوند یا هم‌زمان پیش بروند؟

**تصمیم کاربر:** Backtest و Shadow هم‌زمان با توسعه اجرا شوند؛ پس از عبور از کنترل‌های ایمنی اولیه، معاملات واقعی شروع شود تا ربات در زمان باقی‌مانده کار کند.

**نتیجه طراحی:** Live منتظر اثبات آماری قطعی سود نمی‌ماند (با 48 ساعت ممکن نیست)، اما در نبود denylist واقعی، تأیید account/API، schema سفارش، stop policy و order reconciliation باید قفل بماند.

### 2.11 دسترسی‌ها و اجرا

- کاربر تأیید کرد API Key حساب اعتباری والکس و دسترسی مدل ابری را دارد؛ دسترسی واقعی و permissionهای لازم هنوز با read-only API call اثبات می‌شوند.
- runtime پیشنهادی VPS/سرور ابری است.
- سفارش‌ها پس از یک بار فعال‌سازی Live و قبولی preflight کاملاً خودکارند؛ تأیید انسانی تک‌تک سفارش‌ها مطلوب نیست.

### 2.12 انتخاب معماری LangChain بدون مدل Pydantic مستقیم

- کاربر خواست معماری به LangChain تغییر کند؛ مستندات با LangChain به‌عنوان orchestration لایه Agent هم‌راستا شد.
- کاربر پرسید آیا Pydantic را می‌توان حذف کرد؛ تصمیم: در کد دامنه هیچ مدل مستقیم Pydantic تعریف نشود، از TypedDict/JSON Schema با قابلیت LangChain نسخه قفل‌شده استفاده شود و Validator صریح Python قواعد تجاری را کنترل کند.
- وابستگی ترانزیتی Pydantic که ممکن است LangChain/provider نصب کند حذف اجباری نمی‌شود. TypedDict به‌تنهایی runtime validation نیست.

## 3. معیارهای ارزیابی ثبت‌شده

جدول کامل از ۳۰۰ امتیاز در `DECISION_REGISTER_FA.md` آمده است. خلاصه: ۱۵۰ امتیاز عملکرد معاملاتی (سود نهایی ۹۰، کنترل ضرر ۳۰، فعال بودن ۱۵، پایداری ۱۵)؛ ۱۵۰ امتیاز کیفیت فنی (منطق استراتژی ۴۰، استفاده واقعی از AI ۳۵، مدیریت ریسک/سرمایه ۳۰، اجراپذیری مجدد ۲۵، Backtest/Shadow ۲۰). کاربر همچنین حجم معاملات را برای گزارش/نظارت و جلوگیری از Self-Trading را به‌طور خاص گوشزد کرد؛ turnover در گزارش ثبت می‌شود، اما در جدول امتیازهای ارسالی ردیف مستقل نداشت.

## 4. گزینه‌ها و اجزای خارج از دامنه MVP

- معماری چندایجنتی بزرگ، LangGraph سفارشی، یا فراخوانی LLM برای هر نماد/tick.
- معاملات مارجین، لوریج، short-selling و مشتقات.
- تحلیل فعال خبر/فاندامنتال در نسخه اول.
- تولید یا اجرای خودکار کد استراتژی تازه در Live.
- UI پیچیده پیش از تکمیل موتور، ریسک، reconciliation و logging.
- فرض اتصال آماده برای Wallex از Freqtrade/Hummingbot یا مخازن دیگر بدون Spike واقعی.
