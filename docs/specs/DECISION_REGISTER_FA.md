# دفتر تصمیم‌های Grill-me — Wallex Opportunity Agent

نسخه: 1.0 · آخرین تجمیع: 2026-10-22

این سند حافظه تصمیم‌های محصول در طول گفت‌وگوی Grill-me است. تصمیم‌های قطعی از پیشنهادهای موقت فنی و چیزهایی که هنوز تأیید نشده‌اند جدا شده‌اند.

## 1. هدف، مسابقه و موفقیت

- پروژه، Agent معاملاتی خودکار برای هکاتون AI Agent استار کوچ/والکس است.
- زمان پیاده‌سازی قبل از شروع کارکرد مورد انتظار کمتر از سه روز بود؛ برنامه توسعه به ۴۸ ساعت فشرده شده و پس از آن ربات باید مدتی اجرا کند تا داده کافی برای گزارش معاملات جمع شود.
- هدف صرفاً «ساخت چت‌بات» نیست: موتور معاملاتی واقعی، قابل‌مشاهده، قابل‌کنترل، قابل‌تکرار و قابل‌ارزیابی باید تحویل شود.
- هیچ استراتژی یا معماری‌ای سود را تضمین نمی‌کند؛ انتخاب‌ها باید با Backtest و Shadow سنجیده شوند.

## 3. تصمیم‌های کاربر که تثبیت شده‌اند

1. **حساب:** حساب اعتباری اختصاصی هکاتون؛ دسترسی API حساب در اختیار تیم است. با وجود نام حساب، معاملات نسخه اول Spot و بدون لوریج‌اند.
2. **سرمایه/اعتبار:** `task.md` مبلغ ۵,۰۰۰,۰۰۰ تومان را سرمایه مبنای چالش می‌نامد؛ PDF دقیق‌تر می‌گوید «۰ تومان دارایی ورودی + ۵,۰۰۰,۰۰۰ تومان اعتبار دریافتی برای ۳ روز». این مبلغ را ۵ میلیون پول تیم + ۵ میلیون اعتبار نشمارید؛ حساب و available balance واقعی باید از API خوانده و با شرایط طرح تطبیق داده شود.
3. **بازارها:** از `assets.md` برای تشخیص بازارهای غیرفعال/ممنوع استفاده شود. فهرست نهایی قابل معامله برابر بازارهای فعال/Spot قابل معامله در API، منهای denylist و محدودیت حساب است.
4. **اجرای سفارش:** کاملاً خودکار بعد از فعال‌سازی Live و preflight؛ تأیید دستی هر سفارش مدنظر نیست.
5. **مدل:** مدل API ابری در اختیار است.
6. **محیط:** VPS یا سرور ابری.
7. **ایده اصلی:** اسکن چندبازاری؛ در هر بازار ممکن است فرصت باشد یا نباشد؛ هر بازار به‌صورت مستقل تحلیل می‌شود.
8. **فعالیت تطبیقی:** ایجنت نباید منتظر «فرصت عالی» نامتناهی بماند؛ فرصت‌های معمولی اما قابل‌قبول را هم می‌تواند بگیرد، ولی نباید آستانه را تا معامله با مزیت خالص نامثبت پایین بیاورد.
9. **تخصیص سرمایه:** تطبیقی بر اساس کیفیت سیگنال، نوسان، نقدشوندگی، ریسک و سرمایه آزاد. تصمیم از کل سرمایه آزاد قابل‌استفاده گرفته می‌شود، نه فقط پول آزادشده از معامله قبلی.
10. **پوزیشن‌ها:** چند پوزیشن هم‌زمان مجاز است؛ exposure و risk کل پرتفوی سقف دارند و تمام موجودی وارد بازار نمی‌شود.
11. **افق زمانی:** تطبیقی بر اساس شرایط همان بازار و ریسک؛ تایم‌فریم کندل و زمان نگهداری باید در تعریف فنی جدا باشند.
12. **سطح خودمختاری:** نسخه اول استراتژی‌های موجود را انتخاب و پارامترهای مجاز را تطبیق می‌دهد (Option B). حرکت تدریجی به تولید/آزمایش استراتژی جدید (Option C) مدنظر است، اما تغییر اساسی قبل از Backtest/Shadow نباید خودکار به Live وارد شود.
13. **خروج:** راهبرد ترکیبی؛ Agent می‌تواند خروج تطبیقی پیشنهاد کند، اما حد ضرر، محدودیت زمان، drawdown و kill switch قطعی و مستقل هستند. برای ساده‌سازی MVP، `EXIT` کل مقدار باقی‌مانده پوزیشن را می‌بندد؛ خروج جزئی خارج از دامنه است تا قرارداد جداگانه تعریف/تست شود. بازبینی AI پوزیشن باز در صفی اولویت‌دار انجام می‌شود و کنترل‌های سخت هرگز منتظر LLM نمی‌مانند.
14. **یادگیری:** عملکرد هر استراتژی در هر بازار جدا بررسی شود، ضمن اینکه شرایط کلی و ریسک کل پرتفوی نیز در نظر گرفته شود.
15. **تحلیل زیان:** هر ضرر باید همراه دلیل ورود/خروج، شواهد و طبقه‌بندی علت `confirmed / likely / unknown` لاگ شود. علت نباید از طرف AI جعل شود؛ یک خبر بیرونی فقط در صورت شاهد معتبر ثبت می‌شود.
16. **اخبار:** نسخه اول روی قیمت، کندل، حجم، اسپرد، عمق، نقدشوندگی و نوسان تمرکز دارد. خبر/فاندامنتال به نسخه بعدی موکول شده، چون بازه کوتاه است و خبر ممکن است پس از اثرگذاشتن بر بازار دریافت شود.
17. **تست:** Backtest و Shadow موازی با توسعه اجرا می‌شوند. Live بعد از پاس‌شدن گیت‌های ایمنی آغاز می‌شود، نه بعد از اثبات آماری قطعی سودآوری.
18. **گزارش:** پس از دو روز توسعه، ربات باید در طول پنجره مجاز کار کند تا گزارش معاملات، نتایج و لاگ‌ها جمع شوند.
19. **ابزار توسعه:** LangChain برای Agent؛ Matt Pocock/AI Hero skills برای ساخت Spec و Ticketهای کوچک، TDD، implement و review؛ Codex مدنظر است و Antigravity نیز ممکن است استفاده شود.

## 4. قوانین و محدودیت‌هایی که در گفت‌وگو به بریف نسبت داده شده‌اند

- Spot و بدون لوریج در محدوده این نسخه.
- معاملات دستی در جریان رقابت، معاملات هماهنگ درون‌تیمی، Self-Trading و Wash Trading ممنوع معرفی شده‌اند؛ متن دقیق قوانین باید پیش از Live با PDF/task اصلی تطبیق داده شود.
- سود نهایی در بریف/گفت‌وگو بر مبنای سود تحقق‌یافته تأکید شده است؛ سود تحقق‌نیافته باید جدا گزارش شود. برای افت سرمایه، منحنی equity/mark-to-market جدا نگه داشته شود.
- هیچ سقف ریسک رسمی از سمت برگزارکننده از طرف کاربر اعلام نشده است. تیم باید کنترل‌های داخلی را برای مدیریت سرمایه و امتیاز «کنترل ضرر» طراحی کند؛ مقادیر پیشنهادی `.env.example` قوانین رسمی مسابقه نیستند.
- جزئیات تسویه پوزیشن باز در پایان چالش باید در قوانین اصلی بررسی شود؛ بسته نباید بی‌مدرک فرض کند همه پوزیشن‌ها اجباری بسته می‌شوند.

## 5. تصمیم‌های فنی پیشنهادی (نه قوانین رسمی)

- یک سرویس Python واحد و ماژولار؛ نه microservice و نه multi-agent swarm در MVP.
- LangChain `create_agent` با یک Decision Agent و خروجی ساختاریافته `TypedDict` یا JSON Schema.
- بدون تعریف مدل Pydantic در کد دامنه؛ Validator قطعی Python برای قواعد تجاری. ممکن است Pydantic به‌صورت dependency ترانزیتی LangChain/FastAPI نصب شود و نباید به‌زور حذف گردد.
- REST برای endpointهای کنترل/سفارش و WebSocket رویدادمحور برای داده زنده در صورت تأیید endpoint و subscription/rate limits.
- Backtest، Shadow و Live باید feature/strategy/risk semantics مشترک داشته باشند.
- SQLite WAL، logهای ساختاریافته، dashboard حداقلی و runbook VPS.
- برنامه baseline اسکن در `AGENT_CONTRACT_FA.md`/`MARKET_SCANNING_DECISION_LOGIC_FA.md` است؛ مقدارها باید در Spike اندازه‌گیری شوند.

## 6. مواردی که هنوز حقیقت قطعی محسوب نمی‌شوند

- endpoint، authentication header، schema دقیق، rate limit و رفتار `client_id` در API جاری والکس تا زمان ثبت شاهد/response در `WALLEX_API_NOTES.md` تأیید نشده‌اند.
- denylist دقیق از اصل `source_materials/originals/assets.md` استخراج و در JSON/CSV مشتق‌شده ثبت شده است؛ قبل از Live hash و شمارش آن را تأیید و با universe فعال Spot در API ترکیب کنید. اگر اصل با derived mismatch داشت یا API universe تأیید نشد، Live ممنوع است.
- provider/model ابری، structured-output support، latency p50/p95 و هزینه هر فراخوانی باید در Spike اندازه‌گیری شود.
- دسترسی، عمق و resolution تاریخچه کندل باید با API جاری اثبات شود؛ داده فرضی نباید به‌عنوان Backtest واقعی گزارش شود.
- baseline ریسک، scan cadence، freshness threshold و horizonها تنظیم اولیه‌اند، نه مقادیر بهینه اثبات‌شده.


## 7. یافته‌های جدید از فایل‌های اصلی که دوباره دریافت شدند

- `assets.md`: معاملات Spot و بدون لوریج؛ ۳۴۵ جفت‌ارز به عنوان بازارهای غیرفعال در حساب اعتباری. فهرست دقیق در `source_materials/derived/inactive_markets.json` و اصل در `source_materials/originals/assets.md` است.
- PDF صفحه اول: API در حساب اعتباری فعال نشان داده شده، اما معامله تعهدی و قابلیت بومی بات معامله‌گر فعال نشان داده نشده‌اند. ربات سفارشی ما می‌تواند از API استفاده کند، مشروط به تست دسترسی واقعی.
- PDF صفحه دوم: fee معاملات حساب اعتباری از سطح ۱ است؛ با liquidation دارایی/مبلغی بازنمی‌گردد. بنر ۳ روز رایگان با توضیح عمومی کارمزد اعتبار ۳۰روزه هم‌زمان است؛ مقدار کارمزد باید برای طرح واقعی تأیید شود.
- PDF انتقال از حساب اصلی به اعتباری را راه پیشگیری از liquidation ذکر می‌کند و جدول انتقال را در ستون حساب اصلی فعال نشان می‌دهد؛ این با انتقال یک‌طرفه main→credit سازگار است. عملیات واقعی باید پیش از اتکا تأیید شود و انتقال credit→main فرض نشود.
- `task.md` درباره valuation نهایی هم از unrealized P&L سخن می‌گوید و هم realized Toman/no coin at end را الزام می‌کند. این دو در telemetry جدا گزارش می‌شوند و روش رسمی با برگزارکننده تأیید می‌شود.
- `task.md` جدول داوری را «پیشنهاد امتیازدهی» می‌نامد؛ در برنامه این بسته از جدول ارائه‌شده توسط کاربر به‌عنوان rubric کاری استفاده می‌کنیم.
